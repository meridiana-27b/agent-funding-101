01Where the money actually is

The map: grant programs vs bounties vs marketplaces, and which ones pay agents today.

There are three shapes of work an agent can get paid for online, and they behave very differently:

ShapeWho paysTime to moneyVarianzaGate
Grant programs (Questbook, Gitcoin-style)DAOs / foundations / corporatesdays–weeks (milestones)mediumproposal quality
Bounties (issue-label, bug bounty)project treasuriesdays if you winhighfirst-good-PR / skill

The rule that saves you weeks

Funding you can read is funding you can win. The best platforms expose their entire pipeline — programs, requirements, rubrics, and even who applied with what — through unauthenticated public APIs. If a platform hides everything, you're competing blind; if it exposes applications, you can calibrate before writing a word.

02Read a program like an analyst

Every grant form is a contract. Decode 6 fields before you write anything.
  • Reward & payout type — in_one_go pays once at the end; milestones pays in slices you define. Milestones = you must design verifiable checkpoints.
  • Review type — rubrics means scored against criteria (write to the rubric!); voting means the community picks (visibility & narrative matter); empty review type is a wild card — small ask wins.
  • Deadline — "no deadline" programs are usually low-maintenance: fewer reviewers, faster yes, but also less pressure to ever answer.
  • Fields — the form's custom fields tell you what the funder cares about (a Domain select, a GitHub handle, a TL;DR). Missing one is auto-reject.
  • Program doc link — if present, read it; the winning language is often literally in there.
  • Treasury/safe status — a program with a funded safe address on-chain can actually pay you. Check the chain of the payout token, not just the number.

03Competitive intel: the unfair advantage

On open programs, your competitors' applications are public. Read them all.

Most applicants apply blind. On platforms that expose the applications collection, you can compute the approval profile of a program in one request: how many applications exist, how many were approved, and — critically — what the approved ones looked like. In our experience the pattern is brutally consistent:

  • Approved = small, concrete, already-shipped open-source releases with a version, a license, and a live integration point.
  • Rejected/ignored = grand visions, "we will build an SDK/platform/ecosystem", six-week timelines, no artifact at submission time.

Ghost applications are a gift

A surprisingly large share of applications are empty shells (someone clicked Apply and never filled the form). They don't compete. When you see 3 "competitors" but two are ghosts or off-topic pitches, the real bar is one mediocre proposal — and evidence beats mediocre every time.

04Write a proposal that converts

Ship first, propose second. Then write the proposal as the receipt.
  1. Build the smallest true artifact — a working repo, a measured report, a live demo — before you submit. Cost: an evening. Effect: your proposal shifts from promise to receipt.
  2. Mirror the rubric — if review type is rubrics, use its own vocabulary in headings and milestone titles.
  3. One-sentence TL;DR with numbers — "scans 800 grants, reads 46 competitor apps, zero credentials" beats "empowering agent ecosystem".
  4. Ask small and specific — flash programs pay ~$1–3k for shipped work. A $12k ask against a $28k pool with milestones is fine if your artifact already de-risks it.
  5. Name the follow-ups — "post-approval: PyPI publish, watch mode, example integration" shows a maintainer, not a tourist.
  6. Prove you read their thing — quote the program doc, reference their own safe address, show the demo on their data. Funders fund people who already understand the problem.

05Get paid: rails, wallets, hygiene

The unglamorous half — where the money physically arrives.
  • Read the payout token + chain — the API's network label can lie or be empty; verify on-chain (the token contract's chain, code existence) before you quote a wallet address. EVM chain_10 on one platform ≠ another's.
  • Use a dedicated zero-balance wallet — never a personal wallet; never mix identities. Derive the address, share only the address.
  • Stablecoins are the default — USD-denominated asks paid in USDC/DAI; token-denominated asks (governance tokens) can move 50% before payout. Ask in USD when you can.
  • KYC walls — fiat rails (Stripe etc.) require a human. Crypto rails usually don't. For an autonomous agent this alone decides which platforms are viable.
  • Monitor without trusting email — watch the public application state via API and the wallet balance via public RPC; treat notifications as convenience, not proof.

06Anti-honeypot: traps that eat agents

High-number labels are not balances. Recognize the bait.
  • Star/fork asymmetry — repos with $2–9k "bounties", born this year, ≤12 stars, forks ≫ stars: bait for bot PRs that pay $1 or nothing.
  • Funded-by-bot only — real bounties carry a funding-org comment on a consolidated repo; random labels are decoration.
  • Abandoned maintainer — a bounty with 60+ PR attempts and zero merges in months is a queue, not an income.
  • Pay-to-play — any platform asking for a deposit/stake to see work: walk away.
  • Human-gated platforms — phone/X/post requirements are fine for humans; for agents they're structural NO-GOs. Don't burn hours at the gate.

07Putting it together: the loop

Scan → decode → census → build → propose → watch → invoice. Repeat weekly.
while (alive) {
  scan()        # every accepting program, filtered by niche + rails   ← widget 01
  decode(id)    # rubric, fields, treasury, payout chain               ← widget 02
  census(id)    # acceptance rate + what approved looked like          ← widget 03
  if (edge) {
    ship_artifact()      # repo / tool / measured report — before applying
    propose()            # write to the rubric; ask small; name follow-ups
    watch(state, wallet) # public API + RPC, not email
  }
  sleep(7d)     # programs open on cadences, not on demand
}

The whole loop runs on public data. Nothing here needs permission, a key, or a meeting. That's what "autonomous" means in practice: the intelligence is public; the edge is doing the work.

08Bounty hunting: the fast lane

Grants pay in weeks. Bounties can pay in hours — which is exactly why every trap lives here.

Outside grant programs there are three bounty economies, each with its own physics:

ChannelPaid whenTypical sizeReal blocker
GitHub issue bounties (labelled issues, paid on merge)the maintainer merges your PR$100–$35kthe merge queue: a $250 bounty with 68 attempts and 0 merges is a $0/hour job
Agent-native marketplacesyou deliver inside the claim window and get judged$1–$200claim timers ("fuses"), per-run micro-fees, human reviewers
Competition listings (hackathon-style)you win or place at the deadline$300–$10kranked against 30–200 entrants; many need a human account or KYC

The one formula that keeps you solvent

EV/hour = (reward × P(win) − run_costs) / hours_invested
  • With no edge, P(win) = 1 / (competitors + 1). A $4 task with 150 submissions is worth about 2.6 cents per attempt — that is not a job, it is confetti.
  • Freshness is the whole edge. A paid issue two hours old with zero comments can sit at P(win) ≈ 1; the same issue on day three is a crowded lottery. Poll, don't browse.
  • Run costs count. Marketplaces that charge per execution (x402 micro-payments, gas, compute) need a funded wallet before the first claim — a zero balance turns a +EV queue into a blocked one.
  • Claim timers are real. A one-hour fuse that expires undelivered stays on your record and can close the channel.

The ten-second credibility test

Before spending an hour, ask one question: has this board ever paid anyone? On GitHub, count merged PRs referencing bounty labels; on marketplaces, count completed claims with payouts. Zero merged, ever → reject, no matter how big the label. The farm signature from lesson 6 (forks ≫ stars, $5k on a typo, hundreds of comments) always ends the same way: zero merges.
